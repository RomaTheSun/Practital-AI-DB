## Висновок

- Режим A описує той самий JSON лише в промпті, а режим B додатково передає нативну схему. В обох режимах стенд перевіряє відповідь класом `StorageLabel` із забороною зайвих полів.
- Для Ollama не припускається конкретний механізм обмеженого декодування: висновок про валідність буде зроблено лише з фактичної частки `schema_valid=true`.
- Схема гарантує форму, але не правильність мітки; це окремо показує колонка «валідно, але хибно».
- У режимі A `score.clean` прибирає суцільну Markdown-огорожу `json` і блоки `<think>…</think>` перед Pydantic-валідацією. Між прогонами A і B очищення не змінюється.
- Числовий висновок і кількість ID, що змінили правильність між A і B, буде додано після завершення локального та хмарного прогонів.

## Чому це може не відтворитися

- Ollama може змінити реалізацію `response_format`; документація підтверджує приймання JSON Schema, але не описує механізм декодування.
- Навіть за фіксованих параметрів версія сервера, модель або квантування можуть змінити відповідь.
- На малому наборі різниця між A і B може бути нульовою; це не доводить загальну еквівалентність режимів.
- Нативний Gemini API і OpenAI-сумісний API мають різні поля, облік токенів та причини завершення; стенд зводить їх до спільного `Turn`, але серверні зміни можуть вплинути на результат.
